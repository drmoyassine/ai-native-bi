title: Columns are discovered from the file and matched by name; a person approves what is not exact
status: accepted
context: >-
  The first transform was written for the made-up test shape (DEC-011); a real .xlsb export failed in dbt with "column
  term_code does not exist". Fixing column names in the models would make every new export a code change.
decision: >-
  Raw keeps whatever columns a file has. A dataset declares the parts it needs (bi.mapping.SHAPES: needed or optional,
  with the names exports tend to use). On every load the parts are matched to the latest file's columns: by the part's
  own name first, then by those aliases. If every needed part is matched by its own name, the mapping is approved by
  that fact; otherwise it is stored as proposed, the upload is `loaded` with a note listing the columns found, and
  nothing is built until a person approves or corrects the mapping (Uploads page, PUT
  /app/api/datasets/{dataset}/mapping), which queues a rebuild. dbt reads the approved mapping as the variable
  <dataset>_columns (macro `mapped`). Files with another layout than the latest cannot be read through one mapping: the
  upload fails naming those files, and analytics stay as they were.
rationale: >-
  No export has to be edited or the code changed; a wrong guess never builds KPIs without a person (CLAUDE.md rule 6);
  raw stays immutable. A mapping is a small, reviewable thing, unlike generated SQL.
consequences: >-
  Which dataset a file is (its kind) is still chosen at upload; discovering that, and building new datasets and their
  metrics from a file, is agent step 2b (TASK-013). One mapping per dataset: mixed layouts in one dataset need a mapping
  per file layout (not built).
