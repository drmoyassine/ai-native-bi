## DEC-012 — One chart definition, rendered with ECharts

---
id: DEC-012
title: One chart definition, rendered with ECharts
status: accepted
context: >-
  Charts are built three ways: by the agent in chat, by API, and by people dragging fields in the app; and handed to
  consumers by API.
decision: >-
  Every chart is one JSON chart definition of the BI's own schema: a Cube query (measures, dimensions, filters, time)
  plus the visual (type and which field goes on x, y, colour, size) and its labels. The agent, the API and the
  drag-and-drop builder all produce and edit this definition. One translator turns it into Apache ECharts options; the
  app renders them in the browser, and a small server-side renderer (Node, beside Cube) makes PNG or SVG for consumers.
  Consumers get the definition with its data, or the image.
rationale: >-
  One kind of object whoever built it: checked against a schema, approved, versioned, handed out. Neither the agent nor
  the API writes raw ECharts options, which are large and can carry JavaScript functions (code). One renderer keeps a
  chart identical in the app, the API and a report. The builder lists only governed fields from Cube's metadata, so a
  hand-built chart cannot use an ungoverned number.
consequences: >-
  The chart definition schema is a contract of the BI, versioned like one. The library sits behind the translator and
  can be swapped. The builder uses Cube's metadata API, Cube's JavaScript client, dnd-kit and react-grid-layout. Image
  rendering adds a Node service.

## DEC-014 — The app: the BI's own accounts, a cookie session, a React app served by the API

---
id: DEC-014
title: 'The app: the BI''s own accounts, a cookie session, a React app served by the API'
status: accepted
context: >-
  Real data comes in through the app (DEC-011), the agent will live in it (ROADMAP-003) and charts are drawn in it
  (DEC-012). Single sign-on comes later (ROADMAP-005).
decision: >-
  The app is a React and TypeScript single-page app (Vite, ECharts) in web/, built into the API image and served by the
  API at /, with its API under /app/api. People sign in with the BI's own accounts (Argon2id); the first account is made
  from the command line (no default accounts). A session is a random token in an HttpOnly, SameSite=Strict cookie,
  stored only as its SHA-256; every request that changes something must also carry the header X-BI-App: 1. Uploads go
  through the worker's load job; charts are chart definitions checked against Cube's governed members.
rationale: >-
  One origin (no CORS, a strict cookie works), one image to deploy, and the same governed path for people as for the
  agent. Server-side sessions can be ended at once; a custom header on writes defeats forged cross-site requests.
consequences: >-
  Node builds the web app (Docker stage, CI job) as well as running VEF. Sign-in has no throttling yet (TASK-010), and
  accounts are created from the command line until the app manages them (TASK-011).

## DEC-030 — Databases load incrementally with history (scd2); files stay snapshots

---
title: Databases load incrementally with history (scd2); files stay snapshots
status: accepted
context: >-
  Copying Banner's large tables in full on every sync is slow and grows without end; the AMS asks for figures as of a
  date.
decision: >-
  Each database sync reads only rows changed since the last (a cursor on a change column, such as Banner's activity
  date) and merges them with dlt's scd2 strategy (_dlt_valid_from, _dlt_valid_to), so the current state and any past

  a slower schedule closes rows that were deleted. Files stay snapshots: each file is the state on its as-of date.
rationale: Small, fast syncs with history kept as validity windows instead of copies.
consequences: Each table needs a chosen cursor or a full read; deletes are seen only at the reconciliation.
